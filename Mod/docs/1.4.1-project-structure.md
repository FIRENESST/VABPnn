# 1.4.1：工程结构整理

本版为 1.4.0 的工程整理补丁。PNN、CSR、秒 / 分钟图 Transformer、JEPA、贝叶斯鼠标、参数数量、优化器和推理 / 学习 / 操作规则保持一致。模型文件继续使用 release-1.4.0.bin（v8 / 19 parts / 522,109,692 字节），不新增参数、重置训练或另做存档迁移。

## 目录与职责

| 位置 | 职责 |
| :--- | :--- |
| CUDAkernel/SelfCudaKernel/SelfCudaKernel/ | 原 CUDA / VS 工程，物理源码位置保留 |
| 同目录 ActionContracts.h | 15 项动作、位移建议与 40 字节最终控制包的共享类型 |
| Mod/native/capture_bridge.cu 与原 .h | JNI / GL / CUDA 生产桥接、checkpoint 和旧动作迁移 |
| Mod/native/tests/ | 原 16 个 CUDA 数值、模式和 checkpoint 程序 |
| Mod/native/benchmarks/ | 原每帧预算基准 |
| Mod/native/build/ | 工具链、缓存、生产链接、验证执行脚本 |
| Mod/build.gradle | Loom / 依赖 / Java / 资源 / 发布配置 |
| Mod/gradle/native.gradle | JNI 构建、资源打包、完整原生 source JAR、CUDA 验证入口 |
| Mod/gradle/verification.gradle | 窗口、GL/JNI 和 Minecraft 临时世界验证 |

VS 仅整理虚拟分组：Contracts、Vision、Temporal、Representation、Learning、Connectivity、Telemetry。补齐 BlockControllers / MemeState 等原来未正确分组的文件。CUDA 实现仍在原目录，后续算子可继续在原 VS 工程编写。

JEPA 的头文件显式依赖 NeuronModel 和 ActionContracts，避免为了使用 MotionProposal 而间接包含完整 Transformer。OnlineLearning 对 TemporalDecision 改为显式引用。共享类型移动前后的字段、大小、命名空间与动作索引不变。

## 构建与验证

在 Mod 根目录运行：

```powershell
.\gradlew.bat --offline build
.\gradlew.bat --offline nativeTest
.\gradlew.bat --offline nativeBenchmark
.\gradlew.bat --offline scopeUiSmokeTest memeScopeUiSmokeTest glCaptureSmokeTest runClientGameTest
```

原入口 native/build-native.ps1 及 -TestOperator / -Benchmark / -OperatorRoot / 工具链参数保留。默认 build 仍只打包生产代码，验证 opt-in；既有 build/native 程序路径不变。满分钟与监控压力档可运行：

```powershell
.\build\native\frame_budget_benchmark.exe --minute-stress --meme-stress --block-stress --meme-scope
```

缓存按实际编译参数、工具链、源文件、项目头文件依赖及目标文件 SHA256 校验。不同 GPU 架构的 production / test 缓存继续分开。头文件只使引用它的编译单元失效；测试 / 基准的链接结果也缓存。修改验证程序不改生产实现，重复执行验证可直接复用程序。系统 CUDA / JNI / CCCL 版本头及直接以引号引用的 SDK 头继续参与校验，未知 include 宏保守回退到全项目头集合。

Mod/native/build/ 内的构建源码在 Git 忽略规则中显式保留；Mod/build/ 仍只存放生成物。

共享 build/native 缓存使用进程间文件锁，避免 Gradle 与原生脚本同时写同一个 .pending.obj / DLL。进程退出自动释放锁；构建产物继续留在 build 中。source JAR 递归打包原生实现、共享头、测试、基准和构建脚本，测试 class 与 DLL 不进入生产 source 文件集。

## 架构保持与验证依据

核对原 10 个 CUDA .cu 与 JNI capture_bridge.cu 的 SHA256，要求逐文件一致。16 个原 CUDA 验证和性能基准只移动，原文件 SHA256 保持不变；模型各字段布局仍由原 static_assert 与 checkpoint 验证约束。

执行既有 GPU 数值 / 冻结 / 动态结构验证、窗口与实际 GL/JNI、v8 模型兼容恢复和 Minecraft 全流程回归；再次核对预算。更换新 JAR 后模型仍从原 v8 文件继续，1.4.0 JAR 保留为 .disabled，其他历史文件不覆盖。

## 本版验证结果

- 原 28 个 CUDA 文件（11 个生产实现、16 个验证、1 个基准）的 SHA256 与整理前完全一致。三个调整依赖的模型头文件，还原 include 与共享类型位置后与原声明逐字一致；28 个生产 Java 文件除两处窗口版本标题外保持一致。
- 16 组 CUDA 验证全部通过，覆盖梯度、AdamW / EMA、冻结权重、动态高贡献点 / CSR、动作选择和 checkpoint。重复执行时 production / test 均 compiled=0、reused=10，16 个验证程序全部命中链接缓存；模拟头文件变更的依赖失效和并发构建锁检查也通过。
- 两个普通 Windows 监控窗口、真实 GL / JNI、无 MSAA / 4x MSAA、背压、缩放、显存连续操作、Minecraft 15 项动作、背包鼠标示范、Ctrl / Shift、F8 / F9 和只预测模式均通过。
- 用整理前真实训练的 v8 模型做 JNI 冷恢复，分钟学习 844 步、贝叶斯鼠标 830 步完整恢复。冻结评估后的 11 个神经权重 / 学习状态 part（含新的分钟与贝叶斯鼠标 part）与原文件逐字节一致。
- 8 个已观测分钟摘要 + 成熟模因 / 排名 / 突变 / 监控压力测试共 2,560 帧，完整复制 / 算子 / 控制链最高 8.1804ms；常规四档 2,048 帧最高 8.4500ms。两次超出 10ms 的帧数均为 0。单客户端 Minecraft 实测算子最高 8.149ms、超预算 0；这项时间不包含 Minecraft 自身渲染。
- 模型与监控显存 628,146,219 字节，与 1.4.0 相同。完整 JAR 与 source JAR 成功构建，77 个随包源码逐文件核验，内嵌 DLL 与本地构建的 SHA256 一致。

核验记录在 build/structure-1.4.1-artifact-proof.json，部署记录在 build/structure-1.4.1-deployment.json；build 下的记录与测试 checkpoint 只用于本机验证。
